# Chap Chap Pay : notes d'intégration (lues le 21 octobre 2026)

Source : la Référence API (`/api`, accessible après connexion à un compte), son fichier OpenAPI `/api/swagger-filtered.json` et le guide `/guide/`. Résumé en mots propres : aucune clé, aucun mot de passe, aucun numéro réel n'est noté ici. **Le fichier OpenAPI est « filtré » selon le compte : les opérations PULL et PUSH y sont absentes (leurs chemins existent, sans opération), alors que leurs modèles de données y figurent.**

## Ce qui est confirmé

- **URL de base** : `https://chapchappay.com/api`. Deux clés distinctes, **test** et **production** (chaîne hexadécimale de 64 caractères, en-tête `CCP-Api-Key`) ; le mode est déterminé par la clé. Un second secret, l'**Encryption Password** (page « Clés API »), sert à signer.
- **Signature** : `CCP-HMAC-Signature` = HMAC-SHA256 hexadécimal minuscule du **corps brut** exact, clé = Encryption Password. Exigée sur les requêtes POST ; les lectures (GET) ne signent pas. Même algorithme pour les **webhooks reçus** (vérifier sur les octets bruts, comparaison à temps constant).
- **Encaisser (E-Commerce)** : `POST /ecommerce/create`, corps `{ amount, order_id (4 à 64, alphanumérique, - et _), description, callback_url, return_url, cancel_url, fee_handling ('deduct' | 'add'), options }`. Réponse 201 : `operation_id`, `payment_url` (page hébergée où le client choisit son moyen et paie), `payment_methods`. `options["jump-to-payment-method"]` envoie directement vers `orange_money` ou `mtn_momo` ; `options["disabled-payment-methods"]` masque des moyens. Le lien **expire après 72 heures**.
- **Lire** : `GET /ecommerce/{operation_id}` et `GET /ecommerce/order/{order_id}` : statut (`new`, `pending`, `success`, `canceled`, `failed`, `error`, `expired`), montant, transaction.
- **Frais** : `fee_handling = 'deduct'` : frais déduits de ce que reçoit le marchand (Speedfood) ; `'add'` : ajoutés au montant du client. **La décision « frais supportés par Speedfood » correspond à `deduct`.** Le taux réel n'est pas dans la référence.
- **Webhook** (`callback_url`, HTTPS public obligatoire, pas de localhost) : corps JSON `{ order_id, operation_id, amount, description, status: { code, description }, transaction: { payment_method, payment_method_reference, payer_info, payment_reference, payment_description, transaction_date } }`. Réponse attendue : 2xx en moins de 20 secondes. Reprise automatique (jusqu'à 5 fois, 5 à 60 s) seulement si le serveur est injoignable ; une réponse HTTP, quelle qu'elle soit, met fin aux tentatives. **Il n'y a pas d'identifiant d'événement** : l'idempotence se fait sur `operation_id` + `status.code`.
- **`success` est définitif et n'arrive qu'une fois ; `failed`, `error` et même `canceled` peuvent être suivis d'un `success`** (le client réessaie, ou l'opérateur confirme tard). Il ne faut donc **pas** clore un paiement sur `failed` ou `error`.
- **Comptes de test** (clé test seulement) : PayCard 111000001 (échec …002) ; Orange Money 720000001 (échec …002) ; MTN MoMo 760000001 (échec …002) ; Soutra 730000001 ; Kulu 740000001 ; Akiba 750000001 ; carte 2303779999000275 (échec 4663295942784758, CVV 123, expiration 02/année future) ; OTP de confirmation **0000** (PayCard, Akiba). **Avec un vrai numéro mobile money et une clé de test, 1 000 GNF sont réellement débités : n'utiliser que les numéros de test.**
- **Compte** : `GET /account/info`, `GET /account/transaction` (paginé), `GET /account/agent/{access_code}` (solde, `can_do_push`, `can_do_pull`, `can_do_payout`, canaux).
- **Règlements** : `POST /payout/{access_code}/request` (`payout_amount`, `agent_pin`, `payout_mode` : `wallet_transfer`, `check`, `bank_transfer`, `other`, `payout_data` : `wallet_type` + `wallet_account_number`, ou RIB, ou chèque) ; statuts `new`, `auto_processing`, `en_cours`, `sent_to_bank`, `check_dropped_off`, `executed`, `canceled`, `failed` ; annulation par `DELETE …/request/{id}` ; `GET` pour lire. Ce sont des **demandes de retrait du solde du compte marchand** vers une destination, avec le code PIN d'un agent API.
- **PUSH** (« envoyer de l'argent aux clients, partenaires ou employés ») : modèle `{ account_number, amount, payment_channel (paycard, orange_money, mtn_momo, cash, kulu, soutra_money, akiba), account_name, order_id, callback_url, fee_handling }`, chemins `/push/{access_code}/check|request|request/{request_id}`, signature obligatoire, **solde suffisant exigé**. Statuts d'une requête : `initiating`, `pending`, `success`, `error` ; une erreur peut survenir **sans webhook** (il faut interroger le statut). Il faut un **Agent API** avec la permission PUSH (code d'accès à 6 chiffres + PIN à 4 chiffres) et le service « API Push » activé sur l'entreprise.

## Ce qui manque ou pose problème

1. **Aucun endpoint de remboursement** dans la référence. Un remboursement automatique ne peut donc pas être garanti ; l'option évidente est un PUSH vers le numéro du payeur, mais ce numéro n'est pas dans le webhook (`payer_info` est un libellé). **Tant que ce point n'est pas éclairci avec Chap Chap, tout remboursement part vers un humain.**
2. **Le solde existe chez Chap Chap Pay, au nom de Speedfood** : l'argent encaissé s'y accumule, et les versements (PUSH ou règlement) en sortent. L'architecture dit « Speedfood ne détient aucun solde » ; en réalité Speedfood est titulaire d'un compte marchand où transite l'argent de tiers (restaurants, livreurs). C'est exactement la question juridique 10 à 15 de `docs/CADRE-JURIDIQUE-LIVREURS.md` : à poser à l'avocat **avant** tout argent réel, et à Chap Chap (cantonnement du solde, agrément).
3. **PUSH et Payout dépendent d'activations** : service « API Push » sur l'entreprise, Agent API avec permissions. À demander à `sales@chapchappay.com` (compte « Speedfood » créé, **vérification d'entreprise (KYC) à 0 %** : indispensable pour la production).
4. Frais réels, délai de mise à disposition du solde, limites par transaction ou par jour : non publiés.

## Ce que cela change dans le code (lot P5, à faire)

- `encaisser` : `POST /ecommerce/create` avec `fee_handling: 'deduct'`, `order_id` = notre référence interne, `jump-to-payment-method` selon l'opérateur choisi, `callback_url` = `/api/paiement/notification/chapchap`, `return_url` = page de suivi.
- `verifierNotification` : signature HMAC hex du corps brut ; identifiant d'événement = `operation_id:status.code` ; **`failed` et `error` ne ferment pas le paiement** (statut « en attente » conservé jusqu'à l'expiration de notre côté), `canceled` peut être suivi d'un `success` (la machine l'accepte déjà), `expired` ferme.
- Notre délai d'expiration (15 min) est plus court que les 72 h du lien : un succès tardif est déjà remboursé automatiquement par le service. **À remplacer** par un remboursement humain tant que le remboursement n'existe pas (point 1).
- `verser` : PUSH, une fois activé et documenté ; sinon règlement par `wallet_transfer` avec `payout_data` du bénéficiaire (à confirmer avec Chap Chap).
- Secrets (jamais dans le dépôt) : `CHAPCHAP_CLE_API`, `CHAPCHAP_CLE_SIGNATURE` (Encryption Password), plus, pour les versements, le code d'accès et le PIN de l'agent API.

## Essai réel en mode test (21 octobre 2026)

Premier encaissement de test de bout en bout avec l'adaptateur (clé de test, compte de test MTN MoMo `760000001`, 3 000 GNF) : création de l'opération, paiement sur la page hébergée, passage à `success` observé par interrogation du statut, transaction visible dans `/account/transaction`.

**Constats** (une seule mesure, en mode test : à recouper avec d'autres montants et en production) :
- **Minimum d'un paiement : 3 000 GNF** (refus 400 en dessous). Pris en compte : l'adaptateur déclare `montantMinimumGnf = 3000` et le paiement en ligne n'est pas proposé en dessous.
- **Commission : 260 GNF sur 3 000 GNF** (environ 8,7 %), déduite du solde (3 000 → solde 2 740). C'est très au-dessus de la simulation de Speedfood (1,5 à 1,7 %) : à mesurer sur plusieurs montants (par exemple 10 000 et 30 000) pour trouver la formule (frais fixe + pourcentage ?) avant de décider du modèle économique du paiement en ligne.
- **`payer_info` contient le numéro du payeur** (dans la transaction ; le webhook documente le même champ) : un remboursement par PUSH vers le payeur serait possible une fois l'API Push activée.
- **Le choix d'opérateur de la page prime sur `jump-to-payment-method`** : l'essai demandé en Orange Money a été payé en MTN MoMo ; le moyen réellement utilisé est dans `status.payment_method`, à journaliser (la notification le porte aussi).
- Une annulation par le client (`canceled`) est bien reçue comme telle ; le script de suivi doit rester actif jusqu'à l'issue (la première tentative a été manquée parce que le suivi avait expiré avant le paiement).
