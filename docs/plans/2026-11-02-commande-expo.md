# Commande dans l'application Expo — plan (2 novembre 2026)

Objectif : permettre de PASSER une commande réelle depuis l'application Expo (aujourd'hui : catalogue réel + panier réel + suivi/annulation, mais pas d'envoi). Condition pour envisager de remplacer l'APK Kotlin (voir `2026-11-01-remplacement-apk-expo.md`). Rien ne remplace `apps/web/public/speedfood.apk` ici.

## Contraintes globales
- Réponse à Malika en français ; code, tests et commentaires dans le style du dépôt (français, sans dépendance nouvelle sans raison).
- Aucun prix envoyé : le serveur recalcule ; on n'envoie que `sousTotalAffiche` (GNF entier) pour comparaison. Montants GNF en entiers.
- Aucune commande RÉELLE ni appel à la production pendant le développement : tests avec `fetch` simulé / faux serveur (`apps/mobile/src/donnees/faux-serveur-*.mjs`).
- La commande se poste à `ORIGINE_CATALOGUE + '/api/v1/commandes'` avec `Authorization: Bearer <accessToken>` (jeton porteur strict) ; le corps suit `CreationCommandePayload` (`packages/shared/src/contracts/commande.ts`) ; `mode` ∈ `retrait` | `livraison` (jamais `sur_place` : l'API le refuse). 201 = nouvelle commande, 200 = rejeu idempotent ; la réponse contient `reference` et `jeton` (clé d'accès au suivi : jamais journalisée, jamais dans une URL).
- `cleIdempotence` générée UNE fois par tentative d'envoi et réutilisée pour tout rejeu (double appui, réseau coupé) ; jamais régénérée automatiquement après une réponse inconnue.
- `consentementReglement: true` doit être une case cochée explicitement par le client (règlement hors portail, confirmation par le restaurant).
- Le jeton de suivi reçu alimente l'écran de suivi déjà existant (`CompteReel.tsx`, `commandes.ts`) sans le dupliquer.
- Pas de `style={{…}}` de mise en page ; tokens de `apps/mobile/src/design/tokens`.
- Un test qui ne peut pas échouer ne prouve rien : mutations demandées pour les gardes (clé d'idempotence, mode refusé, double envoi).

## Lot A — envoi d'une commande en RETRAIT (ce lot)
1. Domaine pur testable : construction du payload à partir du panier réel, des coordonnées (nom, téléphone) et du consentement ; règles de validation côté client (nom non vide ≤ 100, téléphone au format accepté par `packages/shared/src/commande/telephone.ts`) ; table des refus serveur → messages en français (400 validation, 401, 409/prix changé, 429, 5xx, réseau).
2. Client API : méthode `creerCommande` dans `apps/mobile/src/connexion/client.ts` (même mécanique `requete`, un seul essai, délai, taille de réponse bornée).
3. Écran de validation de commande (depuis `PanierReelVue`) : récapitulatif, champs, consentement, bouton Envoyer désactivé pendant l'envoi et tant que le formulaire est invalide ; exige d'être connecté (sinon renvoi vers la connexion) ; en cas de succès : vider le panier, afficher la référence et ouvrir le suivi de CETTE commande.
4. Gestion d'un envoi incertain (délai dépassé, réseau coupé après envoi) : conserver la même clé d'idempotence ; proposer « Réessayer » (même clé) et « Vérifier mes commandes ».
5. Tests, typecheck, relecture indépendante.

## Lot B — livraison (adresse, quartier, frais estimés par le serveur, `destination`, `fraisAffiches`)

### Exigences du lot B (écrites le 2 novembre 2026 après lecture du serveur)
Constats : le site (`apps/web/src/app/commande/page.tsx`) lit les quartiers en base (« Quartier, Commune », `quartierId` = identifiant du quartier) ; l'APK Kotlin les lit par la table publique `neighborhoods` ; **l'API unique n'expose aucune liste de quartiers** (`apps/api/src/routes/catalogue.ts` : seulement `/restaurants` et `/restaurants/:id/menu`). L'estimation existe : `POST /api/v1/livraison/estimation` `{restaurantId, destination, sousTotal}` → `{ok, estimation}` avec `estimation` = `{statut:'non_calcule'}` | `{statut:'ok', fraisGnf, distanceKm, gratuite, dureeMinutes, libelle}` | `{statut:'erreur', message}` (jeton porteur strict). À l'envoi, le serveur recalcule ; si `fraisAffiches` ≠ frais serveur → 409 `CONFLIT_ETAT` (message avec le nouveau montant, `fraisServeur`). Si `non_calcule` (interrupteur éteint) : frais 0, pas de `fraisAffiches` exigé. Adresse de livraison : 5 à 300 caractères.
1. **API (code seulement, NON déployé)** : route publique en lecture `GET /api/v1/catalogue/quartiers` → `{ok:true, quartiers:[{id, libelle:"Quartier, Commune"}], luLe}` triés par libellé (même source que le site : hiérarchie communes + quartiers ; requête recopiée dans `apps/api/src/catalogue/`, pas d'import du site), contrat dans `packages/shared/src/contracts/catalogue.ts`, tests `apps/api/tests`, mutations. Aucun déploiement sans feu vert de Malika.
2. **Mobile, domaine pur** : mode `livraison` dans `commande-reelle.ts` (adresse 5–300, `quartierId` obligatoire, `destination:{quartierId}`, `fraisAffiches` = frais du dernier calcul serveur, absent si `non_calcule`) ; `sur_place` toujours refusé ; l'empreinte de la tentative (clé d'idempotence) inclut mode, adresse, quartier et frais affichés ; refus 409 « frais changés » : afficher le nouveau montant, exiger une nouvelle confirmation, **nouvelle clé** seulement après ce refus explicite (le 409 prouve qu'aucune commande n'a été créée).
3. **Client** : `listerQuartiers()` et `estimerLivraison(restaurantId, quartierId, sousTotal, accessToken)`, un seul essai, délai, réponse bornée.
4. **Écran** (`CommandeReelle.tsx`, `PanierReelVue.tsx`) : choix Retrait ou Livraison ; en livraison : adresse, quartier (liste filtrable), frais et durée estimés lus du serveur (recalculés si sous-total ou quartier change ; la dernière demande remplace les précédentes), total = sous-total + frais « estimé », envoi bloqué tant que l'estimation manque ou est en erreur ; l'échec de lecture des quartiers n'empêche pas le retrait.
5. Tests (mutations : frais non transmis, mauvais mode, estimation périmée, nouvelle clé hors 409), typecheck exit 0, relecture indépendante, commit et push de la branche de travail seulement.
## Lot C — paiement : déclaration du règlement après acceptation par le restaurant (modes et codes marchand fournis par le suivi), sans paiement en ligne tant que Chap Chap Pay n'est pas ouvert

### Exigences du lot C (écrites le 2 novembre 2026 après lecture du serveur)
Constats : Speedfood ne reçoit jamais d'argent ; le client règle le restaurant (code marchand Orange Money / MTN MoMo, ou espèces) puis DÉCLARE ; le restaurateur CONFIRME (`packages/shared/src/paiement/regles.ts` : `optionsPaiement`, `paiementOuvert`, `peutDeclarer`, `lireReferencePaiement`, `libelleStatutPaiement`). Le suivi (`POST /api/v1/suivi`) fournit déjà `paiement:{statut, mode, reference, declareLe, recuLe, options:[{mode, libelle, code}], enLigne}`. **La déclaration n'existe que comme action serveur du site** (`apps/web/src/lib/commande/actions.ts`, `declarerPaiementAction(jeton, mode, referenceBrute)`) : **aucune route `/api/v1`**. Contrôles de l'action, à reproduire à l'identique : jeton valide ; mode ∈ `especes|orange_money|mtn_momo` ; référence 4–40 caractères simples ou vide ; plafond `limiterDeclarationPaiement` ; commande trouvée par jeton ; `paiementOuvert` (commande acceptée, sans proposition active) sinon 409 ; `peutDeclarer` sinon 409 ; refus si paiement en ligne déjà ouvert/abouti ; le mode doit figurer dans `options` du restaurant ; jamais de montant venu du client ; écriture `orders.paiement_*`.
1. **API (code seulement, NON déployé)** : `POST /api/v1/suivi/paiement` `{jeton, mode, reference?}` → `{ok:true}` ; sans identité (jeton de suivi = clé), sur le modèle de `/suivi/annuler` dans `apps/api/src/routes/suivi.ts` ; service injecté dans `deps.suivi` (`apps/api/src/types.ts`, `worker.ts`) qui RÉUTILISE la logique du site (extraire une fonction de service commune appelée par l'action ET par la route : pas de copie divergente) ; contrat dans `packages/shared`, mêmes codes d'erreur et messages ; tests + mutations (mode refusé, paiement non ouvert, déjà confirmé, paiement en ligne en cours, mode absent des options, plafond).
2. **Mobile, domaine pur** : types du suivi étendus à `paiement` (lecture stricte, valeur inconnue = refus d'affichage) ; fonction pure « que peut faire le client » (déclarer / modifier / rien, libellé) à partir de `statut`, `paiement` et `proposition` ; référence validée comme le serveur ; refus serveur → messages français.
3. **Client** : `declarerPaiement(jeton, mode, reference)` dans `connexion/client.ts`, un seul essai, délai, réponse bornée, jamais de relance automatique ; le jeton de suivi jamais journalisé ni mis dans une URL. Idempotence : la déclaration est naturellement rejouable (écrasement du même état) ; après réponse inconnue, relire le suivi avant de proposer de réessayer.
4. **Écran** (`CompteReel.tsx` / écran de suivi existant, sans le dupliquer) : après acceptation, bloc « Régler le restaurant » : modes proposés avec leur code marchand (copiable à l'oeil, texte sélectionnable), champ référence facultatif pour mobile money, bouton « J'ai payé » / « Je paierai en espèces », état « déclaré, en attente de confirmation du restaurant », « reçu » ; rien avant l'acceptation ; mention claire « Speedfood ne reçoit pas votre argent » ; aucun paiement en ligne (`enLigne.disponible` ignoré/affiché comme indisponible).
5. Tests, mutations, typecheck exit 0, relecture indépendante, commit et push de la branche de travail seulement. Déploiement de la route sur feu vert distinct de Malika.
